# План: веб-чаты как транспорты llm-rotator + режим сервиса

Статус: этапы 0–8 реализованы (0.3.0); не сделаны 5.4 (hedging) и 9 (другие сайты).
Дата плана: 2026-11-03.
Целевая версия: `llm-rotator 0.3.0`.

Документ написан так, чтобы по нему мог работать исполнитель без контекста
исходного обсуждения. Каждый этап — законченный кусок с критериями приёмки.
Этапы выполнять **по порядку**; внутри этапа — сначала тесты на моках, потом код.

---

## 0. Цель и рамки

Один инструмент, который:

1. ротирует **API-ключи** (то, что llm-rotator умеет уже сейчас);
2. использует **веб-чаты через аккаунты** (DeepSeek Web первым, затем Qwen,
   DuckAI и другие) — каждый сайт отдельным транспортом (`api_style`);
3. держит **каждый аккаунт на своём прокси** (существующая связка
   `Binding = key@proxy`, ключ никогда не ходит через чужой адрес);
4. работает **и как библиотека** (обратная совместимость с 0.2.0), **и как
   сервис** — OpenAI-совместимый HTTP-эндпоинт для харнессов.

Источник идей — проект FreeDeepseekAPI (Node.js, MIT,
`/home/lirix/FreeDeepseekAPI`). Код **не копируется**, а переписывается на
Python; ссылки вида `server.js:NNN` ниже указывают, где смотреть логику.

### Что исправляем относительно FreeDeepseekAPI (требования пользователя)

| # | Проблема в FreeDeepseekAPI | Причина (проверено в коде/вживую) | Что делаем |
|---|---|---|---|
| R1 | Удалённые чаты копятся (>2000 чатов за 2 дня на одном аккаунте) | Нет ни одного вызова удаления: `resetRemoteSession` (`server.js:483`) лишь забывает id; каждый сброс/повтор/параллельный запрос создаёт новый чат | Реестр своих чатов + удаление брошенных (этап 4) |
| R2 | Новый чат харнесса отвечает про прошлый проект | Все клиенты с localhost без `user` попадают в один `agentId='dev-agent'` (`server.js:2773`); `planSessionTurn` (`server.js:2520`) шлёт запрос без сообщений ассистента **дельтой в старый удалённый чат**; плюс подмешивается `buildRecoveryHistoryPrefix` (`server.js:2314`) | Изоляция по пространству имён клиента + переиспользование чата **только при доказанном продолжении** (этап 3) |
| R3 | Запрос минуту и больше ждёт недоступный аккаунт | На другой аккаунт уходят только при 401/403/429 (`server.js:443`); таймауты 60 с (`server.js:39`); ошибки приходят **в HTTP 200** и не распознаются | Классификация ошибок в теле 200, короткий таймаут до первого события, немедленный уход на другую связку с полным контекстом (этапы 2, 5) |
| R4 | Большие контексты режутся (лимит 80k символов, `server.js:282`) | Лимит сильно занижен | Большой контекст — файлом (этап 6) |

### Ограничения, которые нельзя нарушать

- **Не трогать чаты, которые создал не llm-rotator.** Удалять можно только чаты
  из собственного реестра. Никакой «массовой чистки» аккаунта — пользователь
  делает это сам.
- Значения токенов/cookie **никогда** не пишутся в логи, ошибки, `/status`.
  В логах — только имя ключа (`key_name`) и имя прокси.
- Живые тесты против реальных сайтов — только с явного разрешения пользователя
  и только опционально (`LLM_ROTATOR_LIVE=1`); CI гоняет моки.
- Публичный API 0.2.0 (`ModelRunner.complete/stream/send/request`,
  `load_registry`, форматы TOML) остаётся рабочим. Новые поля — опциональные.

## 1. Проверенные факты о DeepSeek Web (2026-11-03)

Проверено живым скриптом на трёх аккаунтах, напрямую (без прокси).

**Заголовки** (см. `server.js:312`): `Authorization: Bearer <token>`,
`Cookie`, `x-hif-dliq`, `x-hif-leim`, `x-client-platform: web`,
`x-client-version: 2.0.0`, `x-app-version: 2.0.0`, `Origin/Referer:
https://chat.deepseek.com`, Chrome UA. Auth-файл: JSON с полями
`token, cookie, hif_dliq, hif_leim, wasmUrl, baseUrl`.

**Эндпоинты:**

| Что | Запрос | Примечание |
|---|---|---|
| PoW | `POST /api/v0/chat/create_pow_challenge {target_path}` | перед completion и upload; ответ → заголовок `X-DS-PoW-Response` (base64 JSON) |
| Создать чат | `POST /api/v0/chat_session/create {}` | id в `data.biz_data.chat_session.id` (или `data.biz_data.id`) |
| Ответ | `POST /api/v0/chat/completion` | тело: `chat_session_id, parent_message_id, prompt, ref_file_ids, thinking_enabled, search_enabled, action:null, preempt:false, model_type:"default"`; ответ SSE |
| **Удалить чат** | `POST /api/v0/chat_session/delete {chat_session_id}` | **работает**: `biz_code 0`; потом completion в этот id → `biz_code 1 "invalid chat session id"` |
| Список чатов | `GET /api/v0/chat_session/fetch_page?count=100&before_seq_id=&before_updated_at=` | `biz_data.chat_sessions[]` (`id,title,title_type,model_type,pinned,updated_at`), `has_more` |
| Загрузка файла | `POST /api/v0/file/upload_file` (multipart `file`, PoW с target `/api/v0/file/upload_file`, заголовок `x-file-size`) | затем опрос `GET /api/v0/file/fetch_files?file_ids=<id>` до `status=SUCCESS`; есть `token_usage` |
| Удалить файл | **неизвестно** | исследовать (этап 6.0) |

**Ошибки, приходящие с HTTP 200** — главный источник «зависаний»:

| Сигнал | Где | Смысл |
|---|---|---|
| `{"code":40003,"msg":"INVALID_TOKEN"...}` / `"Authorization Failed (invalid token)"` | JSON-тело любого запроса | токен протух → аккаунт мёртв до перелогина |
| SSE `event: hint`, `data: {"type":"error","finish_reason":"backend_busy", "content":"Сервер занят…"}` | completion | временная перегрузка DeepSeek; видели на **всех** аккаунтах одновременно ~5–10 минут |
| `type:"error"` с текстом про «too many messages» | completion | лимит аккаунта (`server.js:862`, `server.js:3011`) |
| `biz_code 1 "invalid chat session id"` | completion | чат удалён/не существует → создать новый |
| `data.biz_code != 0` вообще | любой | считать ошибкой, разбирать `biz_msg` |

**SSE completion** (логика разбора — `server.js:2929-2990`):
`event: ready` с `request_message_id/response_message_id`; далее `data:` строки
вида `{"v":{"response":{...,"fragments":[...]}}}`, патчи `{"p":"response/fragments","o":"APPEND","v":[...]}`,
`{"p":"response/fragments/-1/content","v":"..."}` и короткие `{"v":"..."}`
(путь `p` наследуется от предыдущей строки), `response/status`
(`INCOMPLETE` = обрезано по длине), `event: close`. Фрагменты `THINK`/`REASONING`
→ reasoning, `RESPONSE`/`SEARCH` → текст. `response_message_id` — это
`parent_message_id` для следующего хода в том же чате.

**Файлы vs сообщение** (тест «иголка» и «6 меток по порядку»):

| Объём | Файлом | В сообщении |
|---|---|---|
| 50k–500k символов | всё найдено, по порядку, 6–11 с | найдено (200k однажды шло 96 с) |
| 1.5M символов (~500k токенов) | **всё найдено по порядку**, ~19 с | **конец потерян** |
| 8.8 МБ и 35 МБ | загрузка `SUCCESS`, `token_usage` одинаковый 1 750 823 → разбор режется на ~1.75M токенов | — |

Подсчёт строк моделью иногда ошибочен (8–9 вместо 6), сами данные — верны.

**PoW** (`lib/pow.js`): WASM `sha3_wasm_bg.*.wasm`; вызов
`__wbindgen_export_0` (alloc), `__wbindgen_add_to_stack_pointer(-16)`,
`wasm_solve(sp, challengePtr, len, prefixPtr, len, difficulty)`, где
`prefix = salt + "_" + expire_at + "_"`; результат: `int32 code` по `sp`,
`float64 answer` по `sp+8`; `code==0` — нет решения. В Python —
пакет `wasmtime`; скомпилированный модуль кэшировать по URL.

## 2. Архитектура

```
             ┌──────────────── service (этап 7) ────────────────┐
 харнессы →  │ HTTP /v1/chat/completions, /v1/models, /status    │
             │ клиенты→namespace, цепочки, SSE                   │
             └──────────────┬───────────────────────────────────┘
                            │ ChatRequest + conversation hint
                    ┌───────▼────────┐
                    │  ModelRunner   │  порядок связок: affinity, LRU, занятость
                    └───────┬────────┘
                    ┌───────▼────────┐
                    │ Gateway.rotate │  паузы, вина: ключ/адрес/провайдер (без изменений по сути)
                    └───────┬────────┘
          ┌─────────────────┼──────────────────────┐
  OpenAIChatTransport   DeepSeekWebTransport   QwenWebTransport …
     (api_style=openai)      │ (api_style=deepseek_web)
                             ▼
                 web/ общий слой: ConversationStore (SQLite),
                 планировщик хода (delta/full/file), эмуляция tools,
                 очередь удаления чатов, кэш загруженных файлов,
                 учёт занятости связок
```

Ключевая идея: **ротатор остаётся stateless по форме** (на вход — полный список
сообщений, как у OpenAI), а состояние веб-чатов живёт внутри общего веб-слоя.
Транспорт для конкретной связки сам решает: есть ли у этой связки удалённый
чат, который доказуемо продолжает этот разговор (→ дельта), или нужен новый
чат с полным контекстом. Переход на другую связку автоматически означает
«новый чат + полный контекст», а старый чат уходит в очередь удаления.

Ядро остаётся **синхронным** (как сейчас: threading + httpx.Client). Сервис
крутит синхронные вызовы в пуле потоков. Переписывать на asyncio — не надо.

### Новая раскладка пакета

```
llm_rotator/
  registry.py        + auth="web_session", key_file, max_concurrent, [providers.*.web]
  gateway.py         + временная недоступность провайдера, хук порядка связок
  transport.py       + TransportContext, регистрация веб-транспортов
  runner.py          + порядок связок для веб-провайдеров, conversation hint
  web/
    __init__.py
    store.py         ConversationStore (SQLite): чаты, очередь удаления, файлы
    fingerprint.py   нормализация сообщений, ключи, контекст-ключ
    planner.py       решение delta/full/file, сборка промпта, бюджеты символов
    tools.py         эмуляция tool calling (промпт + разбор)
    janitor.py       фоновое удаление брошенных и старых чатов
    busy.py          счётчики занятости связок (max_concurrent)
    deepseek/
      __init__.py
      client.py      HTTP-методы DeepSeek (create/complete/delete/upload/list)
      pow.py         PoW через wasmtime
      sse.py         разбор SSE в события
      transport.py   DeepSeekWebTransport (Transport protocol)
      auth.py        захват авторизации через Chrome CDP
  service/
    __init__.py
    app.py           Starlette-приложение
    openai_api.py    разбор/сборка формата OpenAI, SSE
    chains.py        обход цепочки моделей (раньше — забота вызывающего)
    clients.py       токены клиентов → namespace
  cli.py             llm-rotator serve | auth | doctor | discover
```

Новые зависимости — **только как extras**, ядро не тяжелеет:
- `[web]`: `wasmtime` (PoW);
- `[auth]`: `websockets` (CDP);
- `[server]`: `starlette`, `uvicorn`;
- `[impersonate]` (позже, для DuckAI/Qwen при необходимости): `curl_cffi`.

## Этап 1. Конфигурация и реестр

### 1.1 providers.toml

```toml
[providers.deepseek_web]
provider_name = "deepseek_web"
api_style = "deepseek_web"
base_url = "https://chat.deepseek.com"
models_url = ""                 # у веб-провайдеров списка моделей нет
auth = "web_session"

[providers.deepseek_web.web]
# необязательные, значения по умолчанию указаны
inline_max_chars = 200000       # больше — контекст уходит файлом (этап 6)
file_max_chars = 4000000        # больше — Failure.TOO_LARGE
first_event_timeout = 15        # сек до первого SSE-события
idle_timeout = 60               # сек тишины в середине генерации
chat_max_turns = 100            # потом новый чат
chat_max_chars = 600000         # суммарно в удалённом чате, потом новый
chat_idle_ttl = 7200            # сек: брошенный по простою чат удаляется
delete_policy = "abandoned"     # "abandoned" | "after_turn" | "never"

[providers.deepseek_web.web.models]
# имя модели в models.toml → флаги запроса
"deepseek-web"          = { thinking = false, search = false }
"deepseek-web-think"    = { thinking = true,  search = false }
"deepseek-web-search"   = { thinking = false, search = true }
```

- `auth = "web_session"`: новое значение рядом с `bearer`/`none`.
- Таблица `web` целиком опциональна; неизвестные поля — `ConfigError`
  (как сейчас для остальных таблиц).
- `models_url = ""` допустим только при `auth = "web_session"`; discovery
  такие провайдеры пропускает.

### 1.2 keys.toml

```toml
[[keys]]
key_name = "DS_GAMER"                     # имя связки (в логах/статусе)
provider = "deepseek_web"
key_file = "accounts/kirillgamer5555.json"  # путь от base_dir; вместо значения из .env
proxies = ["auto1"]                       # для веб-аккаунта — обычно ровно один
max_concurrent = 1                        # параллельных ходов на связку
```

- Для `auth = "web_session"` поле `key_file` **обязательно**, значение из
  `.env` не читается. Для остальных `key_file` запрещён.
- `Binding.key_value` для веб-связки — **путь к файлу** (строкой), чтение
  файла — дело транспорта (файл может обновиться перелогином без рестарта:
  перечитывать по mtime).
- `max_concurrent` (по умолчанию: 1 для `web_session`, без ограничения для
  остальных).
- Предупреждение на загрузке (не ошибка): два веб-аккаунта одного провайдера
  на одном прокси без `rotates = true` — это «два аккаунта с одного IP».
  Такая проверка частично уже есть (`_shared_proxy_warnings`), расширить.

## Этап 2. DeepSeek: клиент, PoW, SSE (без состояния)

Цель: одна функция «отправить промпт в новый чат и получить ответ» с
правильной классификацией ошибок. Состояние разговоров — на этапе 3.

### 2.1 `web/deepseek/pow.py`
- `solve(challenge: dict, wasm_url: str) -> int` через `wasmtime`; модуль
  компилируется один раз на URL (кэш, потокобезопасный), экземпляр — на
  каждое решение. Таймаут загрузки WASM 15 с; WASM качается **через тот же
  прокси, что и связка** (иначе адрес утекает).
- `pow_header(client, headers, target_path) -> str` — base64 JSON как в
  `server.js:664-689`.
- Тест: известная пара challenge→answer (снять один раз из живого прогона JS
  `lib/pow.js` и записать в фикстуру).

### 2.2 `web/deepseek/client.py` — `DeepSeekClient`
Создаётся на (связка, httpx.Client через прокси связки). Методы:
`create_chat()`, `complete(chat_id, parent_id, prompt, ref_file_ids, flags)
-> Iterator[Event]`, `delete_chat(chat_id)`, `upload_file(name, bytes) ->
file_id`, `ping()` (дешёвая проверка токена: `fetch_page?count=2` — `count=1` сервер отвергает («illegal count»)).

Каждый ответ проверяется на ошибки **в теле** (`code`, `data.biz_code`)
независимо от HTTP-кода; ошибка → исключение `WebError(kind, detail,
retry_after)`, где `kind` ∈ `auth | busy | rate_limit | chat_gone | too_large
| bad_request | upstream`.

httpx-клиент: брать из `Gateway.client(proxy)`? **Нет** — у него один
read_timeout на всё. Завести в веб-слое свой пул клиентов по имени прокси с
`httpx.Timeout(connect=10, read=first_event_timeout)`; idle-таймаут
генерации — вручную в читателе SSE (см. 2.3).

### 2.3 `web/deepseek/sse.py`
- Читатель SSE по строкам с UTF-8 инкрементальным декодером.
- Таймауты: до **первого события** — `first_event_timeout`; между событиями
  — `idle_timeout`.
- Выдаёт события: `Ready(response_message_id)`, `Delta(text|reasoning)`,
  `Finish(reason)`, `Hint(error)`. Логика путей `p` — порт `server.js:2929-2990`.
- `hint` с `finish_reason=backend_busy` → `WebError("busy")`;
  «too many messages» → `rate_limit`; `INCOMPLETE` → `finish_reason="length"`.
- Тесты на фикстурах этапа 0.

### 2.4 Классификация → `Failure` (используется на этапе 3)

| WebError.kind | Failure | retry_after | Почему |
|---|---|---|---|
| `auth` (40003, 401, 403 с JSON) | `KEY` | — | аккаунт мёртв до перелогина; дополнительно `store.mark_account(key, "needs_auth")` |
| `rate_limit` | `QUOTA` | 60 | лимит аккаунта |
| `busy` | `QUOTA` | 30 | + см. «временная недоступность провайдера» ниже |
| таймаут до первого события / обрыв соединения | `PROXY` | — | поведение ротатора: следующий адрес/ключ |
| 403 без JSON (Cloudflare) | `BLOCKED` | — | как у API |
| `too_large` | `TOO_LARGE` | — | следующая модель цепочки |
| `bad_request` | `FATAL` | — | |
| `chat_gone` | не отказ | — | транспорт сам создаёт новый чат и повторяет **в той же попытке** |
| пустой ответ без ошибки | `QUOTA` | 10 | уйти на другую связку, не ждать |

**Временная недоступность провайдера.** `busy` бывает у всех аккаунтов
сразу. Добавить в `SessionState` таймер «провайдер на паузе»:
`suspend_provider(provider, seconds)`, проверяемый в `rotate` рядом с
`provider_available`. Правило: если за 60 с `busy` пришёл от **двух разных**
связок одного провайдера → провайдер на паузу 60 с, обход идёт к следующей
модели цепочки. Сейчас `unavailable` — бессрочный набор; таймерную паузу
сделать отдельным полем, не ломая `forget_models`.

**Готово, когда:** `DeepSeekClient` проходит юнит-тесты на моках
(`httpx.MockTransport`), включая все строки таблицы.

## Этап 3. Разговоры: изоляция и переиспользование чатов (R2)

### 3.1 Пространство имён (namespace)

Каждый запрос несёт `namespace` — кто спрашивает. Разговоры из разных
namespace **никогда** не делят удалённый чат.
- В библиотеке: новый необязательный аргумент
  `runner.complete(..., conversation=ConversationHint(namespace="hermes",
  session="abc"))`. Без него — `namespace="default"`.
- В сервисе (этап 7): namespace = имя клиента по его токену, плюс
  необязательный `X-Session-Id` / поле `user` как дополнительное разделение.

### 3.2 Отпечатки (`web/fingerprint.py`)

- Нормализованное сообщение: `role`, текст контента (части склеены,
  картинки → хеш), для ассистента — tool_calls как `(name, canonical_json(args))`
  **без id** (клиенты их переписывают), для tool — `tool_call_id` заменяется на
  имя инструмента. Reasoning не входит.
- `message_key = sha256(json(normalized))[:16]`.
- `context_key = sha256(system-сообщения + описание tools)`.

### 3.3 Хранилище (`web/store.py`, SQLite, файл `base_dir/state/rotator.db`)

Таблица `chats`:
`chat_id, provider, key_name, proxy_name, namespace, session, context_key,
sent_keys (JSON-массив), parent_message_id, turns, remote_chars, created_at,
last_used_at, state ('active'|'busy'|'abandoned'|'deleted'|'delete_failed'),
delete_attempts`.

Таблица `files`: `key_name, sha256, file_id, created_at` (кэш загрузок —
файл принадлежит аккаунту).

Таблица `accounts`: `key_name, health ('ok'|'needs_auth'), detail, updated_at`.

Потокобезопасность: одно соединение на поток или общий Lock; WAL-режим.

### 3.4 Планировщик хода (`web/planner.py`)

Вход: связка, namespace/session, сообщения, tools. Выход: `TurnPlan`:

- **delta** — существует чат этой связки, где `namespace` и `context_key`
  совпадают, `sent_keys` — **строгий префикс** ключей запроса, а хвост после
  префикса (за вычетом эхо ответа ассистента, который мы же и дали) содержит
  хотя бы одно не-ассистентское сообщение. В промпт идёт только хвост
  (+ напоминание о tools, если они есть).
- **full** — во всех остальных случаях: новый чат, полный промпт. Старый чат
  этого же разговора (если был на этой связке) → `abandoned`.

Запрещено (это и была причина R2):
- «клиент шлёт только новый ввод — дописать в последний чат» без
  совпадения префикса. Запрос `[system, user]` без ассистента **всегда**
  новый разговор.
- подмешивание истории из других разговоров.

Ротация чата (новый чат с полным контекстом) также при: `turns >=
chat_max_turns`, `remote_chars >= chat_max_chars`, `context_key` изменился.

Чат в состоянии `busy` (идёт ход) не переиспользуется: параллельный запрос
того же разговора получает новый чат, который после ответа помечается
`abandoned` (то есть удаляется). Это заменяет «ephemeral»-чаты FreeDeepseekAPI,
которые не удалялись.

Сборка промпта — порт `formatConversation`/`formatMessages`
(`server.js:2436-2495`) и `buildBoundedPrompt` (`server.js:2323`) без
recovery-истории.

### 3.5 Транспорт (`web/deepseek/transport.py`)

`DeepSeekWebTransport.complete(route, binding, request) -> Attempt`:
1. занять слот связки (`busy.py`); если слотов нет — `Attempt(failure=QUOTA,
   retry_after=0, detail="связка занята")` **без** штрафа (см. 5.2);
2. план хода → при необходимости `create_chat`;
3. completion; на `chat_gone` — один раз новый чат с полным промптом;
4. успех → обновить запись чата (`sent_keys` += ключи запроса + ключ нашего
   ответа, `parent_message_id`, счётчики) → `ChatResponse` с `origin`,
   `reasoning`, `tool_calls` (этап 5.3);
5. отказ → `Attempt` по таблице 2.4; чат, начатый в этой попытке, →
   `abandoned`.

`open_stream` — то же, но `LiveStream`-совместимый объект: первый `Delta`
вытягивается до возврата (как делает `OpenAIChatTransport`), чтобы обход
мог уйти на другую связку, пока клиенту ничего не отдано. При наличии
tools ответ буферизуется целиком (tool-call нельзя отдавать по кускам).

`LiveStream` сейчас завязан на openai-чанки. Выделить минимальный интерфейс
(итерация `StreamChunk`, `text`, `finish()` → `ChatResponse`) и сделать
веб-реализацию отдельным классом с тем же интерфейсом; `runner._send`
проверяет `isinstance(..., (ChatResponse, LiveStream))` — расширить проверку
на протокол/базовый класс.

### 3.6 Регистрация транспорта

`TRANSPORTS` сейчас — `factory(gateway)`. Добавить `TransportContext`
(store, пул веб-клиентов, busy-счётчики, janitor) и сигнатуру
`factory(gateway, context)`; `OpenAIChatTransport` контекст игнорирует.
`ModelRunner.__init__` получает необязательный `context`; если не передан и
в реестре есть веб-провайдеры — создаётся по умолчанию (SQLite в
`base_dir/state/`).

### 3.7 Тесты (моки)

- новый разговор `[system,user]` после другого разговора в том же namespace →
  **новый чат** (регрессия R2);
- продолжение (клиент эхом вернул наш ответ + новый user) → дельта в тот же
  чат, `parent_message_id` верный;
- клиент переписал id tool_calls → всё равно дельта;
- изменили system → новый чат, старый `abandoned`;
- два namespace с одинаковыми сообщениями → разные чаты;
- параллельный запрос того же разговора → второй в новом чате, затем
  `abandoned`;
- `chat_gone` → прозрачный новый чат.

**Готово, когда:** все тесты выше зелёные; ручной смоук (с разрешения):
два разных разговора подряд не «помнят» друг друга.

## Этап 4. Уборка чатов (R1)

`web/janitor.py` — фоновый поток (в сервисе — всегда; в библиотеке —
запускается `ModelRunner`, останавливается в `close()`):

1. берёт чаты в состоянии `abandoned`, а также `active` с
   `last_used_at < now - chat_idle_ttl`;
2. удаляет `POST /api/v0/chat_session/delete` **через ту же связку** (тот же
   аккаунт и тот же прокси);
3. успех или `invalid chat session id` → `deleted`; ошибка → `delete_attempts+1`,
   повтор с паузой (1 мин, 5, 30), после 5 попыток → `delete_failed`;
4. связка на паузе за `auth` → не пытаться, ждать перелогина;
5. скорость: не больше 1 удаления в 2 с на аккаунт, чтобы не ловить лимиты.

`delete_policy`:
- `abandoned` (по умолчанию) — удалять брошенные и простаивающие;
- `after_turn` — каждый чат удаляется сразу после ответа (полностью
  stateless режим: всегда full-промпт, никаких следов в аккаунте);
- `never` — не удалять (отладка).

**Не делать:** ничего, что трогает чаты не из таблицы `chats`. `fetch_page`
использовать только для `doctor` (проверка токена), не для удаления.

Запись `deleted` хранится 7 дней, потом вычищается из SQLite.

**Готово, когда:** тесты на моках: брошенный чат удаляется через свою
связку; удаление переживает рестарт (очередь в SQLite); политика
`after_turn` не оставляет чатов.

## Этап 5. Быстрый переход между аккаунтами (R3)

### 5.1 Таймауты
Уже заложено в 2.2–2.3: `first_event_timeout` (15 с) вместо 60 с;
отдельный `idle_timeout` для середины генерации. Ошибки в теле 200
распознаются (2.4) — это убирает «вечные» повторы на мёртвом токене.

### 5.2 Порядок связок для веб-провайдеров (`runner.py`)

Сейчас `rotate` берёт связки в порядке ключей из конфига → весь трафик идёт
в первый аккаунт. Для провайдеров с `auth = "web_session"` перед `rotate`
переупорядочить `route.bindings` (через `dataclasses.replace(route,
bindings=...)`, `gateway` не трогаем; сортировка «сомнительных» в `rotate`
стабильна и порядок сохранит):
1. связка, у которой есть активный чат этого разговора (affinity) — первой;
2. затем свободные (есть слот `max_concurrent`) по давности использования
   (LRU) — равномерная нагрузка;
3. затем занятые.

Занятая связка в попытке возвращает `QUOTA` с `retry_after=0` и пометкой
«занята»; в `Gateway._remember` такую попытку **не штрафовать** (сейчас QUOTA
ставит cooldown). Ввести признак в `Attempt` (`detail` недостаточно —
добавить поле `transient: bool = False`, по умолчанию False, совместимо).

### 5.3 Эмуляция tool calling (`web/tools.py`)

Порт из `server.js:956-1580`: компактные схемы tools, промпт с правилами
формата, терпимый разбор (JSON, DSML/XML-обёртки, ремонт JSON), напоминание
о формате в дельта-ходах. Результат → `ToolCall` ротатора. Тесты — порт
соответствующих кейсов из `tests/unit.test.js` FreeDeepseekAPI.

Повтор «со строгим промптом» при битой разметке (`server.js`, лог «Retrying
with stricter prompt») — делать **в том же чате** ответом-уточнением, а не
новым чатом (иначе снова мусор, R1). Если всё-таки новый — старый `abandoned`.

### 5.4 Дублирующий запрос (hedging) — опционально, в конце этапа

Параметр провайдера `hedge_after` (сек, по умолчанию выключен). Если за это
время нет первого события — параллельно запустить ту же попытку на следующей
свободной связке, взять первый ответ, второй отменить и пометить его чат
`abandoned`. Реализуется в runner поверх двух попыток; в `rotate` не лезть.
Делать только после того, как 5.1–5.3 стабильны.

**Готово, когда:** тест: первая связка «молчит» (мок с задержкой) → ответ
приходит со второй связки за `first_event_timeout + ε`; тест: протухший токен
(200 + 40003) → связка на паузе, в `accounts` — `needs_auth`, второй запрос её
не трогает.

## Этап 6. Большой контекст файлом (R4)

### 6.0 Исследование (с разрешения пользователя, одним скриптом)
- найти эндпоинт удаления/списка файлов (посмотреть Network в веб-интерфейсе
  при удалении файла) — нужен, чтобы не копить файлы в аккаунте;
- проверить, видит ли модель файл из **предыдущего** хода в следующих ходах
  того же чата (от этого зависит, можно ли загружать историю один раз).

**Результаты 6.0 (живой прогон 2026-11-03):**
- Модель видит файл из **предыдущего** хода в следующих ходах того же чата,
  повторно прикладывать его не нужно → историю достаточно загрузить один раз.
- Эндпоинта удаления/списка файлов найти не удалось: угаданные пути
  (`file/delete_files`, `delete_file`, `delete`, `list_files`, `fetch_page`)
  отдают HTTP 200 с HTML, то есть не существуют. Настоящий путь виден только в
  Network веб-интерфейса.
- Файл **переживает удаление чата** (`fetch_files` после удаления: `SUCCESS`).
  Загруженные файлы копятся в аккаунте; ротатор снижает их число: грузит только
  когда контекст не влезает, и один раз на `(аккаунт, sha256)`.

### 6.1 Стратегия (`planner.py`)
Если полный промпт > `inline_max_chars`:
- в сообщении остаются: system-инструкции, описание tools и правила
  формата, **последний ход** пользователя/результат инструмента, короткая
  пометка «полная история — в приложенном файле context.md»;
- в `context.md` — вся предыдущая история в том же текстовом формате;
- большие выводы инструментов (> 20k символов) в последнем ходе тоже уходят
  отдельным файлом;
- если и файл > `file_max_chars` → середина истории обрезается
  (`truncatePromptMiddle`, `server.js:2296`) с пометкой; если всё ещё велико →
  `TOO_LARGE`.

Загрузка: через связку (файл принадлежит аккаунту), кэш `files` по
`(key_name, sha256)`, опрос статуса до `SUCCESS` с дедлайном. Ошибка загрузки
→ `Failure.QUOTA` (короткая) — уйти на другую связку.

### 6.2 Картинки
Порт существующего потока картинок (`server.js:704-816`) тем же механизмом
загрузки; включать параметром провайдера `images = true`.

**Готово, когда:** тест на моках: промпт 300k → в completion уходит короткий
промпт + `ref_file_ids`; ручной смоук: «6 меток» на 1.5M символов через
ротатор находит все.

## Этап 7. Режим сервиса

### 7.1 Запуск
`llm-rotator serve --base-dir DIR [--host 127.0.0.1] [--port 9660]`
(Starlette + uvicorn, extra `[server]`). Один процесс, один `ModelRunner`,
одна `SessionState` на всё время жизни — паузы и аффинити общие для всех
клиентов. По умолчанию слушать только loopback.

### 7.2 Клиенты (`models/clients.toml`)
```toml
[[clients]]
client_name = "hermes"          # → namespace
token_env = "CLIENT_TOKEN_HERMES"   # значение токена в .env
default_model = "chain:main"    # если клиент не указал модель или указал неизвестную
```
Авторизация: `Authorization: Bearer <token>` или `x-api-key`. Неизвестный
токен → 401. Если `clients.toml` нет — один клиент `default` без токена,
только для loopback (как FreeDeepseekAPI без `PROXY_API_KEY`).

Это и есть разделение харнессов: у каждого свой токен → свой namespace →
свои удалённые чаты. Дополнительное разделение внутри харнесса:
`X-Session-Id` или поле `user`.

### 7.3 Эндпоинты
- `POST /v1/chat/completions` — stream и non-stream; `tools`, `tool_choice`;
  `model` = имя модели **или** `chain:<имя>` (цепочка из `chains.toml`).
  В ответе заголовки `X-Rotator-Origin` (`model · provider · key · proxy`)
  и `X-Rotator-Attempts` (число неудачных попыток).
- `GET /v1/models` — модели + цепочки (`chain:*`).
- `GET /health` — жив ли процесс.
- `GET /status` — связки: пауза/причина/сколько осталось, занятость,
  здоровье веб-аккаунтов (`needs_auth`), очередь удаления. Без путей к
  файлам и без значений ключей.
- `POST /admin/reload` — перечитать конфиг (только loopback/админ-токен).
- ~~`POST /v1/messages` (Anthropic)~~ — **отложено решением пользователя**,
  не реализовывать в 0.3.0 (см. «Решения пользователя»).

### 7.4 Цепочки (`service/chains.py`)
Обход моделей цепочки с одним `TurnBudget` на ход (`gateway.turn_budget()`),
`runner.send` на каждую модель, ошибка `GatewayError` → следующая модель,
итог — `gateway.chain_error(...)`. Это то, что сейчас README называет
«задачей вызывающего кода»; сервис становится этим кодом.

### 7.5 Стриминг
Синхронный `LiveStream` итерируется в пуле потоков
(`starlette.concurrency.iterate_in_threadpool`), SSE в формате OpenAI
(`chat.completion.chunk`, `[DONE]`), keep-alive комментарии каждые 15 с,
отмена при разрыве соединения клиентом → закрыть поток (и пометить чат,
если ход не завершён, как `abandoned`).

### 7.6 Ошибки наружу
`GatewayError` → 503 с текстом `chain_error`; всё на паузе по квоте → 429 с
`Retry-After` = `state.waiting()`; неверный запрос (`FATAL`) → 400.

### 7.7 Эксплуатация
- `deploy/llm-rotator.service` — systemd user unit (образец —
  `FreeDeepseekAPI/deploy/free-deepseek-api.service`).
- Паузы `SessionState` сохранять в SQLite при остановке и раз в минуту,
  поднимать при старте (чтобы рестарт не бил снова в мёртвые аккаунты).
- Логи: одна строка на ход — namespace, модель, origin, попытки, время до
  первого токена, режим (delta/full/file).

**Готово, когда:** интеграционный тест (Starlette TestClient + моки
транспортов): два клиента с разными токенами и одинаковыми сообщениями →
разные чаты; стрим отдаёт корректные чанки; цепочка переходит ко второй
модели при `busy` первого провайдера.

## Этап 8. Авторизация и диагностика

### 8.1 `llm-rotator auth deepseek <key_name>`
Порт `scripts/deepseek_chrome_auth.js`: запустить Chrome/Chromium с
отдельным профилем на ключ (`state/chrome/<key_name>`),
`--remote-debugging-port`, и **`--proxy-server=<прокси связки>`** — вход
должен идти с того же IP, через который аккаунт потом работает. Через CDP
(`websockets`) забрать `userToken` из localStorage, cookie, заголовки
`x-hif-*` из сетевых событий, URL WASM. Записать в `key_file` с правами 600.
Ограничение: Chrome не умеет прокси с логином/паролем во флаге — для таких
прокси выдать понятную ошибку (или локальный форвардер — позже).

### 8.2 `llm-rotator doctor`
Для каждой связки: прокси доступен; для веб — `ping()` (токен жив);
для API — `/models`. Итог таблицей; мёртвые веб-аккаунты помечаются
`needs_auth` и подсказывается команда перелогина. Только чтение.

   — только после согласия пользователя; используют связки из его

5. README: разделы «Веб-чаты», «Сервис», «Авторизация аккаунтов»; CHANGELOG

## Решения пользователя (2026-11-03)

- **API наружу — только OpenAI** (`/v1/chat/completions`, `/v1/models`).
  Anthropic `/v1/messages` отложен: в этапе 7.3 пункт про него **не делать**,
  но не закрывать архитектурно (формат ответа собирается в
  `service/openai_api.py`, рядом позже ляжет `anthropic_api.py`).
- **Порт сервиса по умолчанию — `9660`** (9655 занят FreeDeepseekAPI, пусть
  работают параллельно на время перехода). Флаг `--port` и переменная
  `LLM_ROTATOR_PORT` переопределяют.
- **Прокси за аккаунтами пока не закреплены.** Все веб-аккаунты стартуют с
  `proxies = ["direct"]`; прокси пользователь будет назначать по ходу правкой
  `keys.toml` (+ `/admin/reload`, без рестарта). Следствия:
  - предупреждение «несколько веб-аккаунтов одного провайдера на одном
    адресе» (этап 1.2) остаётся **предупреждением**, не ошибкой, и для
    `direct` выводится один раз сводно, а не на каждую пару;
  - `doctor` (этап 8.2) показывает, какие веб-аккаунты сидят на `direct`;
  - команда `auth` без прокси у связки запускает Chrome без `--proxy-server`
    и пишет, что вход сделан с прямого IP (при последующем назначении прокси
    может понадобиться перелогин через него).
- Накопленные чаты в аккаунтах пользователь чистит сам — ротатор их не
  трогает (см. «Ограничения»).
